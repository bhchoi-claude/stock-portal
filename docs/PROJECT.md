## 1. 목적

여러 개로 흩어진 증권 관련 도구를 하나의 화면에서 관리한다.

기존 문제: 도구마다 접속 주소가 달라 관리가 어려웠다.
해결 방향: 화면과 데이터는 통합하되, **실행 프로세스는 분리**한다.

### 범위 밖 (별도 논의)

- 매매 전략의 구체적 내용 (진입·청산 조건, 파라미터 값)
- 미국 주식 자동매매 — 나중에 별도 엔진으로 추가. 지금은 DB 컬럼만 확보
- 리치프랜즈랩 — 별도 서비스. 종목코드·시세만 공유

## 2. 서버 환경

```
호스트    bh-server (LG 그램 14ZD970-G-AX5SK)
OS        Ubuntu 26.04 LTS
CPU       4 cores
RAM       7.1 GB (가용 5.6 GB)
디스크    233 GB (가용 203 GB)
내부 IP   192.168.45.105
접속      Tailscale
```

**서버는 bh-server 단일.** 오라클 클라우드는 사용하지 않는다.

### 접속 방식

Tailscale 오버레이 네트워크로만 접속한다. SK브로드밴드 이중 NAT 환경이라
포트포워딩은 불가능하다.

Tailscale이 이미 인증을 처리하므로 **애플리케이션 자체 로그인은 구현하지 않는다.**

향후 앱 설치가 불가능한 환경(회사 PC 등)에서 접근이 필요해지면
Cloudflare Tunnel + Zero Trust Access를 추가한다. 지금은 구현하지 않는다.

## 3. 시스템 구성

### 프로세스

| 프로세스 | 역할 | 실행 | 관리 |
|---|---|---|---|
| `portal` | 웹 화면 + API 서버 | 상시 | systemd |
| `engine-daytrade` | 단타 매매 | 장중 (09:00~15:30) | systemd + timer |
| `engine-swing` | 스윙 매매 | 장중 | systemd + timer |
| `collector-news` | 텔레그램 + DART 수집·분석 | 상시 | systemd |
| `collector-market` | 시장지표 수집 + 국면 판정 | 일 1~2회 | systemd timer |

### 부속 서비스

| 서비스 | 용도 | 포트 |
|---|---|---|
| Nginx | 리버스 프록시 | 80 |
| PostgreSQL | DB | 5432 (localhost only) |
| 리치프랜즈랩 | 별도 서비스 | 5000 |

### 구조도

```
              [Tailscale 100.x.x.x]
                       │
                    [Nginx :80]
                       │
              ┌────────┴────────┐
         /  → portal:8000    /lab → 리치프랜즈랩:5000
                       │
                 [PostgreSQL]
                  ├ portal_db
                  └ lab_db
                       │
       ┌───────────────┼───────────────┐
  engine-daytrade  engine-swing   collector-news
                                  collector-market
```

**엔진과 수집기는 HTTP 포트를 열지 않는다.** DB를 통해서만 포털과 통신한다.
- 상태 보고: `heartbeat` 테이블에 주기적으로 기록
- 제어 명령: `command` 테이블에 포털이 기록, 엔진이 폴링

이 구조의 이유: 포털이 죽거나 재배포돼도 매매 엔진은 영향을 받지 않는다.

의존 방향이 뒤집힌다. (`INTERFACES.md` 0장)

## 5. 증권사 · 계좌

### 브로커

**키움증권 단일.** REST API 사용 (Open API+ 아님 — 리눅스 환경).

토스증권은 신청만 해두고 사용하지 않는다. 향후 미국장 확장 시 재검토.

### 계좌 분리

전략별 손익을 분리해서 보기 위해 계좌를 나눈다.
증권사 잔고가 곧 전략별 포지션이 되므로 별도 정합성 관리가 필요 없다.

| 계좌 | 용도 |
|---|---|
| 계좌 A | 단타 |
| 계좌 B | 스윙 |
| 모의투자 계좌 | 개발·검증 |

자금 배분은 `config/accounts.yaml`에 둔다. 코드에 하드코딩하지 않는다.

**실제 계좌번호는 `.env`에만 둔다.** `config/`와 DB 어디에도 두지 않는다.
DB 백업 덤프에 평문으로 남는 것을 막기 위한 결정이다. (`SCHEMA.md` 1장)

`config/accounts.yaml`은 `account_id`로 계좌를 참조하며 비밀값을 담지 않는다.
같은 구조의 `config/accounts.example.yaml`은 커밋한다.

### 브로커 어댑터

증권사 종속을 격리한다. 전략 코드는 어느 증권사인지 알지 못한다.
인터페이스 정의는 `INTERFACES.md` 참조.

## 8. 설계 원칙

Claude Code는 아래 원칙을 위반하는 코드를 작성하지 않는다.

### 8.1 매매 엔진은 포털과 독립

포털의 재시작·장애가 매매에 영향을 주면 안 된다.
엔진은 포털의 HTTP 응답에 의존하지 않는다.

### 8.2 파라미터는 설정 파일에서만

손절폭, 익절폭, 진입 금액 등은 `config/`에 둔다.

- 코드에 하드코딩 금지
- **화면에서 변경 불가.** 표시만 한다
- 변경은 파일 수정 + 엔진 재시작으로만 반영

의도적인 마찰이다. 장중에 손실이 나는 상황에서 파라미터를 만지는 것을 막는다.

### 8.3 백테스트와 실전은 같은 전략 코드

전략 클래스는 하나. 데이터 공급원만 교체한다.
백테스트 전용 전략 코드를 따로 만들지 않는다.

```
        [Strategy]
             │
    ┌────────┴────────┐
 과거 데이터        실시간 데이터
 (backtest)         (engine)
```

### 8.4 멀티마켓 대비 (구현은 하지 않음)

미국장을 나중에 붙일 수 있도록 아래만 지킨다. 추가 구현은 없다.

- 종목 식별자에 **거래소** 포함: `KRX:005930` (시장 구분이 아니다)
- 시각은 **UTC 저장**, 표시할 때만 변환
- 통화 컬럼 보유 (현재는 전부 `KRW`)
- 거래소 컬럼 보유 (현재는 전부 `KRX`)
- 시장 구분은 `stock.board`에 별도 보유 (`KOSPI`/`KOSDAQ`)
- 거래시간은 코드에 박지 않고 `exchange` 테이블에서 조회

### 8.5 수집기는 플러그인

소스 하나가 실패해도 나머지는 정상 동작한다.
모든 수집기는 동일한 형식으로 DB에 적재한다.

### 8.6 이력을 남긴다

나중에 검증하려면 과거 값이 필요하다.

- 국면 판정 이력 (날짜, 국면, 점수, 지표값, 당일 시장 결과)
- 키워드 빈도 이력 (급등도 계산의 기준)
- 텔레그램·DART 원문 (프롬프트 개선 후 재분석용)

### 8.7 비용 상한

LLM 호출은 일일 상한을 둔다. 초과 시 자동 중단하고 알림.
무한 루프 버그로 인한 비용 폭주를 막는다.

## 9. LLM 사용 방침

정보수집에서만 사용한다. 가벼운 모델(Haiku)로 충분하다.

### 처리 순서

```
수신
 ↓ 규칙 필터 (광고·중복·짧은 글 제거)
 ↓ 종목명 사전 매칭          ← LLM 미사용
 ↓ 키워드 사전 매칭          ← LLM 미사용
 ↓ 미매칭분만 배치로 LLM     ← 여기만 비용 발생
 ↓ 빈도 집계 → DB
```

- 종목명 추출은 상장사 명단 매칭으로 처리한다. LLM을 쓰지 않는다
- LLM은 **키워드 추출과 동의어 판단**에만 사용한다
- 메시지 단건 호출 금지. 배치로 묶는다 (1~5분 지연 허용)
- 키워드 사전이 쌓일수록 LLM 의존도가 낮아지는 구조로 만든다

## 11. 백테스트

**실행은 CLI, 결과 조회는 포털.**

```bash
python -m backtest run --strategy swing --from 2025-01-01 --to 2025-12-31
```

- 파라미터를 바꿔가며 반복 실행하는 작업이므로 CLI가 적합하다
- 결과는 DB에 저장하고, 포털에서 비교·조회한다
- **수수료와 슬리피지를 반드시 반영한다.** 미반영 시 결과가 무의미하다

### 데이터 확보 순서

분봉은 과거 조회에 제한이 있어 지금부터 쌓아야 한다.
따라서 **일봉 기반 스윙 백테스트가 먼저 가능**하고, 단타는 분봉이 쌓인 뒤에 가능하다.

수집 범위는 관심종목부터 시작해 점진적으로 넓힌다.
전 종목 1분봉은 연 30GB 수준이므로 디스크는 문제없으나 API 호출 한도가 제약이다.

### 수정주가

액면분할·병합·무상증자가 일어나면 과거 가격과 현재 가격이 연속되지 않는다.
조정하지 않으면 분할일이 급락으로 보여 손절이 대량 발동한다.

- 시세 테이블에는 **원주가를 그대로** 저장한다. 실전 대조에 필요하다
- 조정 이벤트는 `corporate_action` 테이블이 정본이다
- `price_daily.adj_factor`는 거기서 계산한 파생값이다
- 백테스트는 조정가로 지표를 계산한다 (`INTERFACES.md` 3.3)
- 거래량도 함께 조정한다. 분할하면 거래량이 늘어난다

배당은 조정하지 않는다. 기록만 남긴다.

### 생존편향

상장폐지 종목을 빼고 백테스트하면 수익률이 과대평가된다.
폐지 종목은 폐지 전에 크게 하락하므로, 영향이 종목 수 비율보다 크다.

- `stock` 테이블에서 **행을 삭제하지 않는다.** `delisted_at`만 채운다
- 폐지 종목의 시세도 지우지 않는다
- 과거 유니버스는 `stock_status`의 해당 시점 값으로 구성한다
- 정리매매 기간도 포함한다. 보유 중 폐지되면 정리매매 마지막 가격으로 청산한다

**초기 백테스트 결과에는 제거할 수 없는 낙관 편향이 있다.**

증권사 API는 통상 현재 상장 중인 종목만 조회할 수 있다. 따라서 Phase 2에서 받는
"일봉 3년치"는 오늘 살아있는 종목의 3년치이고, 이미 폐지된 종목은 빠져 있다.
이 편향은 지금 와서 없앨 수 없다.

앞으로 폐지될 종목은 지금부터 남기면 편향 없이 쌓인다. 분봉과 같은 이유로
종목 명단과 상태를 매일 기록하는 작업이 급하다.

성과를 판단할 때 이 한계를 감안한다. (`ROADMAP.md` Phase 7)

## 12. 배포

### 배포 가능 시간

국내장 기준 **15:40 이후**에만 배포한다. 장중 배포 금지.

향후 미국장 엔진이 추가되면 배포 가능 시간이 16:00~22:00으로 좁아진다.

### 방식

| 대상 | 방식 |
|---|---|
| 매매 엔진 | systemd. 장 마감 후 재시작 |
| 포털·수집기 | systemd. 비교적 자유롭게 재시작 |
| DB 스키마 변경 | 마이그레이션 스크립트. 백업 후 적용 |

### 노트북 서버 운영 설정

24시간 운영을 위해 아래를 적용한다.

- 덮개 닫힘 무시: `/etc/systemd/logind.conf` → `HandleLidSwitch=ignore`
- 절전 비활성: `systemctl mask sleep.target suspend.target hibernate.target`
- **배터리 충전 임계값 60~80% 제한** (상시 100% 충전 시 팽창 위험)
- 커널 자동 재부팅 비활성 또는 장 마감 후로 고정
- 공유기 DHCP 예약으로 내부 IP 고정
- AC 복구 시 자동 부팅 (BIOS)

## 13. 보안

- 서비스 포트는 전부 `127.0.0.1` 바인딩. 외부 노출은 Nginx만
- `ufw`로 불필요 포트 차단
- API 키·토큰은 `.env`에 두고 git에 커밋하지 않는다
- 키움 API 허용 IP 등록 필요 → `curl ifconfig.me`로 공인 IP 확인
  - SK브로드밴드 공인 IP가 유동일 경우 대응책 필요
